# Architecture

The program has one Bubble Tea event loop. `ui.Accounts` owns retained per-account `Model` sessions and one refresh clock. State changes happen in `Update`; views format state and do not perform I/O. `tea.Cmd` closures perform Slack calls and return typed result messages. Configuration writes are small synchronous local-file operations; authentication runs before starting the TUI. No HTTP calls execute inside `View` or a key handler.

| Package | Responsibility |
| --- | --- |
| `cmd/siftpane` | Flags, credential-store/environment access, identity validation, lifecycle |
| `internal/core` | Service interface, conversation/message/page types, filtering, bounded merge, delivery state |
| `internal/slack` | Documented Web API transport, per-method pacing/backoff, coalesced profile lookup, immediate history pages, safe textual Slack content |
| `internal/demo` | In-memory implementation of the identical service interface, pagination, threads, deterministic send failure |
| `internal/store` | Preferences, durable attention/follow identities, disposable display caches and explicitly opted-in fetched message windows; private atomic replacement, no credentials or drafts |
| `internal/ui` | Application state, commands, navigation, drafts/outbox, layout and rendering |

`core.Service` provides identity, direct conversation metadata, paginated discovery, paginated history/replies, and posting. Slack authentication uses a previously authorized user token from the internal app's install flow. `conversations.info` restores included IDs without scanning the directory. The directory is a progressively loaded metadata catalog; timeline history is fetched only for Kept or explicitly opened attention conversations; separately authorized local follows read only their exact thread roots. The optional `Mentions` capability reads bounded search results independently of Kept; it does not synchronize unkept timelines. Demo mode creates a memory-only store and never opens a credential store or network transport.

Every included conversation gets a cancellation context and generation. Removal cancels outstanding reads, invalidates the generation, clears cached content and local notifications, and saves inclusion preferences. Late responses from a removed generation are ignored even after re-inclusion. A send already in progress is allowed to finish because cancellation cannot retract a message Slack may have accepted. Its draft/delivery state survives removal and informs the exit warning.

History cache eviction is LRU, limited to 16 timelines with 300 messages each. Old/new pages deduplicate by Slack timestamp. Recent history refresh replaces its observed timestamp range so changed/deleted messages in that window are reconciled. A selected channel following newest can fetch up to three older pages per opening/manual refresh to fill unused viewport height. This fill retains the newest bounded window and selection, stops at the visible height, exhausted history, failure or a repeated oldest timestamp, and never auto-pages threads. Resize can use any remaining fill budget. Explicit older-page loading retains the older portion of a full cache; newest refresh shifts back toward recent messages. Threads page forward and use an `oldest` watermark after all loaded pages are complete. Incomplete threads require explicit next-page requests. These bounds trade complete historical synchronization for predictable work and memory.

Local-read watermarks are independent of Slack. First observation establishes a baseline; subsequent observed timestamps can set a sidebar dot. Viewing/marking clears it locally. No Slack write occurs for selection or read-state changes. Drafts use conversation/thread keys and remain outside the timeline cache.

The outbox retains an immutable attempt body and stable random client ID. One delivery per target can be pending or failed; duplicate pending submissions are rejected. Acknowledgement clears only the matching draft. A transport-independent delivery-error interface classifies outcomes, including wrapped errors; display strings are never used for retry decisions. Definite failure permits manual retry; ambiguous failure requires an extra explicit retry after warning. Original text stays available for retry or restoration to the composer. Exactly-once delivery across a network failure is not guaranteed. Memory-only drafts are an intentional privacy tradeoff, with an explicit discard warning on exit.

The HTTP layer paces all calls per method with a mutex-protected clock. Each method has a cancelable request queue: selected-view history, selected-conversation metadata, explicit direct opening and active-view profile reads precede queued background work; each priority remains FIFO. Only the eligible head waits on a timer. Priority never interrupts an issued request or advances a pacing/Retry-After deadline. Replacement credentials share queues and deadlines; mutations retain ordinary FIFO ordering. `429 Retry-After` extends that method's deadline, including manual calls. Waiting honors context cancellation. There are no automatic send retries. Automatic reads are bounded round-robin ticks; expired credentials stop refresh. The UI reports transport errors without logging request/response bodies.

The app name and right-aligned workspace plus authenticated `@username` from `auth.test` share a single header row, followed by one blank row separating it from the panes. Rendering uses one shared-edge Unicode outer frame and an inset rounded composer frame. The composer has a prompt, delivery-recovery text when needed, and a solid outline in every state, accented when focused and muted when idle. Rounded corners, solid modal frames, dashed separators, and dotted groups follow the Joshka reference without native cell-border sequences. Layout accounts for two outside columns, the shared column, two outside rows, two composer border rows, composer input rows, and one conversation-context row. When following newest, history places unused vertical space above loaded messages so the newest message stays above the composer; explicit browsing retains its anchored placement. Every scrolling mode keeps the visible tail of a message crossing the top edge, reserving one row for its repeated author. Newest/selection-following windows preserve their selected bottom boundary; positive scroll retains its top reading anchor. It does not discard that message just because it could fit in the pane by itself. Cursor navigation, page scrolling and automatic layout changes never skip the remainder of a loaded message merely to align another header; continuations repeat the author rather than strand body text without context. Below 76 columns the sidebar is a separate focused view. Mouse capture is disabled for native text selection; OSC52 copies only message text.

Current dependency APIs were checked against upstream Bubble Tea v2 documentation and installed module source/type documentation. Versions are pinned in `go.mod`/`go.sum`. No third-party Slack SDK is needed for these few HTTP methods.

The UI is organized by responsibility: `model.go` defines lifecycle/state, `commands.go` captures asynchronous requests, `state.go` manages local selection/cache/drafts, `input.go` and `picker.go` handle keys, and `history.go`, `delivery.go`, and `updates.go` apply typed results. Rendering is divided among layout, sidebar, composer, history, and dialog files. `snapshot.go` is an explicit offline review harness, separate from the pure `View` path. Shared rules live in [development standards](DEVELOPMENT.md) and [UI/UX guidelines](DESIGN.md).

## Value ownership

`core` owns the string-backed conversation kinds and delivery states shared by both services and the UI. Their textual values remain compatible; the preference schema is unchanged. UI focus and picker modes have separate private types, and offline snapshot mode identifiers are a distinct public boundary. The event loop continues to own all runtime state.

Immutable session limits, transport policy, CLI defaults, and layout/key presentation definitions stay in their owning packages and files, as specified by the [value policy](DEVELOPMENT.md#values-states-and-settings). They do not become mutable settings. Thread refreshes reserve every second tick while a thread is open; only conversation ticks advance the round-robin conversation index. Named durations and capacities explain the resource bound, while server backoff and runtime cancellation retain priority.

## Conversation search

Quick search and the include/remove picker share loaded conversation metadata and a single event-loop-owned text input. `core.Filter` understands `@`/`#` scopes; DM metadata retains the available handle alongside its preferred display name from the existing bounded `users.info` cache. No service method, scope, user-directory scan or new-DM creation is added. Directory requests fetch up to 200 conversations and use only cached profiles; a separate single-flight, cancelable, generation-guarded lookup stream decorates unresolved DM names while directory pagination continues. Name lookups are bounded to 512 attempts per picker opening, skipped for `#` queries, and retain visible incomplete coverage after failure or exhaustion. Query changes can resume name enrichment without restarting directory pagination. Opening either picker continues directory pages serially, with cancellation, a generation guard, cursor-cycle detection and a 100-page automatic budget; explicit continuation starts another bounded scan. Directory metadata loading remains separate from included-conversation history polling. A separate account-isolated, whitelisted directory cache restores search hints without cursor/completeness or inclusion state. Entries retain individual observation ages and are revalidated before explicit opening/keeping. Direct channel links/IDs use a cancelable `conversations.info` command and typed result/action, retaining input/drafts on failure and rejecting stale results and workspace mismatches. Pasted URLs are parsed locally and never followed.

The modal is composed with Lip Gloss layers over a color-stripped, dimmed copy of the main view. Rendering remains pure. Input and paste are routed to the modal even if an underlying send is pending. Dismissal restores composer focus; completion never selects/includes; explicit Enter can include-and-open. Asynchronous metadata updates retain the highlighted conversation's ID when list ordering changes. Directory busy/error/coverage state is independent of transient history/send status, and failed pagination preserves its retry cursor.

## Startup restoration

Before the event loop starts, `ui.New` reads the bounded disposable display cache through `store`, filtering it by current inclusion. `Init` schedules the active cached conversation's history alongside metadata restoration and directory discovery, so history does not await a directory scan or all saved metadata. Without a cache, the first available included conversation can start history immediately and its row becomes available for navigation while the other summaries restore. Fresh account-isolated directory hints (the existing 24-hour per-entry limit) defer inactive included metadata until explicit opening. Unresolved DM directory hints inherit a useful saved name/handle from the same account’s included summary; the directory observation retains its participant and other metadata, cached provenance, age and deferred-validation eligibility. Resolved directory labels take precedence. The active conversation and summaries without fresh observations still validate at startup. Successful individual metadata responses renew only their own directory observation. Saving old display summaries does not extend eligibility for deferred validation. Account switch-back rechecks the active conversation plus unresolved/failed metadata, retaining already validated inactive summaries.

The startup sidebar retains its cached list (initially empty on an uncached launch) while saved metadata requests settle, then publishes the grouped, name/ID-sorted result together. Search and message history can use arriving metadata immediately. The first usable automatic selection and explicit include/open actions publish only their target into the startup list immediately, retaining grouped ordering and leaving unrelated pending metadata buffered. Sidebar rendering and keyboard navigation share the same published list; selection remains a conversation ID, independent of metadata sorting. Removal can end the startup wait, and late generations cannot change restoration state. The sidebar reserves a visible row for restoration state even when conversations fill the viewport, keeping the active row in view. Unavailable saved metadata has independent retry state; `R` retries those reads along with the current history. The existing per-method pacing and bounded polling remain unchanged.

Initial history errors stay on their timeline, so unrelated refreshes cannot turn them into an indefinite loading message. Explicit refresh clears that error while requesting a new page; successful empty history is distinct from loading. `store` owns cache schema, byte/entry/age bounds and whitelisted fields; cache writes reuse private atomic replacement independently of preferences. See [configuration and privacy](CONFIGURATION.md).

## Message names and first-page priority

History transport returns the raw bounded message page and Slack links as soon as the history request completes; it performs no author/mention requests. The optional UI-consumed profile service decorates names separately. The event loop schedules at most one name lookup at a time for the active timeline, newest messages first. Switching conversations/threads or removing the lookup's conversation cancels it and invalidates its generation. Late results cannot clear a newer lookup, change selection or drafts, or resurrect a removed timeline. Profile failures retain readable ID fallbacks and are attempted again only on a new focused view or explicit `R`; expired authentication still stops reads. Each focused view/manual refresh permits at most 512 distinct lookups, preventing eviction-driven loops.

The Slack client coalesces concurrent requests for the same user across metadata and message enrichment. Its synchronized name cache retains up to 512 minimal profiles; the UI copies snapshots onto the event loop and persists only changed snapshots. `store` isolates these disposable names by workspace and authenticated user in a separate, privately written cache, with per-entry expiry rather than renewing old identities on each save. Presentation decorates copies of message text, preserving raw cached text and avoiding interpreting display names as Slack markup. Rendering performs no I/O or mutations; clipboard output uses the same resolved names.

While the active conversation's first history request is pending, background ticks defer other timelines without consuming their round-robin turns. Normal rotation resumes after that page or an error, so an inaccessible active conversation cannot starve the rest. Thread rotation, explicit history requests, pacing, `Retry-After`, and send/retry semantics remain intact.

## Keyboard help

The keyboard guide shares the centered opaque/dimmed overlay renderer with search. Event-loop-owned help visibility and scroll offset leave underlying focus, picker, selection and drafts intact. Help handles keys before quit/send/search and blocks paste/input forwarding while still processing resize and service results. Single-column wrapped guide rows and viewport-derived bounds keep all shortcuts reachable; rendering clamps the offset without mutating state. Dismissing help restarts the still-focused composer/picker virtual cursor because help consumes its blink timers. The single status row remains readable below overlays and owns the minimal help entry point. Loading/refresh progress is derived from the selected timeline and metadata-restoration state during rendering, with no I/O or mutations. It replaces idle status in the bottom left while the message area remains clear; unrelated timeline completions cannot erase active loading. Send/authentication recovery and discard/persistence warnings retain priority. Status events carry a typed routine/action kind; explicit-action feedback takes precedence over timeline progress/errors until the next explicit key or status result. Transport progress never gains action priority by matching display strings.

## Attention ownership

`core.AttentionState` owns typed reasons, grouped triggers, Kept, handled identities and replay floor/checkpoints. Trigger keys combine conversation ID with a stable source/message identity inside a workspace/user account file. `store.Attention` loads that versioned durable file; a corrupt file blocks attention changes rather than resetting dismissals. Legacy inclusion migrates as Kept on first account use. The old workspace inclusion map remains a compatibility mirror; account-specific Kept state is authoritative thereafter.

`ui` owns discovery phase, cancellation/generation, in-flight page number/total, and the runtime inclusion union. Kept and explicitly opened attention entries are eligible for history. New discovery entries appear without changing active selection or fetching their history; explicit opening anchors the request and selection to the exact trigger. Commands capture immutable requests and return typed results. Disabling invalidates the generation and cancels reads; late results are ignored. Attention persistence commits a cloned candidate before dismissal or checkpoint publication. Cache eviction cannot discard handled identities or drafts.

Discovery checks a bounded timestamp interval with a two-day overlap, seven-day maximum catch-up, ten-page budget and monotonic replay floor. Partial accepted pages survive failure/restart without advancing the completed checkpoint. A terminal page and successful save commit the interval. Changed totals, failure or exhaustion report incomplete coverage and preserve previous completion. These local mechanics cannot overcome Slack search filters/indexing/collapsing; live acceptance remains separately tracked.

Polling derives eligible conversations from Kept plus explicitly opened attention entries before assigning turns; unopened sidebar discoveries consume no timeline turn. An explicit trigger/target retry replaces the bounded cached window and its pagination metadata, preserving drafts/outbox separately. Discovery authentication failure publishes recovery before stopping reads; anchored context requests respect the same stopped state.

Known catch-up gaps are durable optional bounds in `core.AttentionState`. New missed intervals extend the summary on a cloned candidate before persistence. Successful scans, restart and source toggles do not erase it. `Ctrl+G` acknowledgement confirms the current bounds twice and clears only that record after a successful save; intervening keys cancel and changed bounds require renewed confirmation.

## Multi-source attention and fast resume (0.6)

`core.AttentionReason` extends the existing reason set with channel/here broadcasts and followed replies. All automatic triggers retain the 0.5 `mention:TIMESTAMP` identity within a conversation/account, so the same message discovered through several paths groups once and durable dismissal applies across sources. A pending duplicate can upgrade its primary reason in deterministic order: direct mention, channel, here, reply. The sidebar shows one row and a count of additional distinct triggers; exact roots remain opening targets. Manual temporary additions retain independent random identities.

The event loop owns the enabled search source queue. One cancelable scan runs each opted-in source sequentially with the existing per-source page budget, stable interval and pagination validation. Completion commits only after all enabled sources terminate successfully. Changing any source invalidates the running generation; enabling revisits the supported interval subject to the monotonic replay floor. Partial pages stay durable on failure; old-source results cannot advance the new source. Pruning considers local-follow checkpoints before removing shared handled identities.

`followed.go` owns a separate single-flight round-robin scanner for at most 32 explicit roots. It starts a due root on startup/ticks (at most one new root per three-second tick), at least three minutes between starts for that root. A window uses exclusive `oldest`/`latest` with a one-microsecond lower padding and local [from, until) filtering, an immutable upper bound, up to ten cursor pages and a seven-day catch-up cap. Only a validated terminal page commits its watermark. Partial pages commit identities first; retry starts at the preceding completed watermark. Roots/self replies and out-of-window messages are filtered locally. Unfollow/unkeep cancels and invalidates the scanner; stale results cannot recreate a follow. Access/grant failures remain visible without modifying membership, Slack subscriptions or read positions. No thread bodies enter durable follow state or the message cache.

`message_cache.go` restores opted-in Kept conversation windows before starting commands, using ID placeholders if display metadata is missing. The timeline tracks cached versus live provenance and its fetched time independently of Busy/Loaded/error. Cache loading bypasses activity observation and the outbox. Only fresh recent fetched pages (not buffer contents that might include a send) qualify for persistence. Store filtering and limits enforce scope again. A cache epoch invalidates persistence from in-flight reads after clear/disable/revocation; conversation generations continue to handle removal/re-inclusion. Authentication stops/cancels reads and purges disk content while retaining drafts/send recovery. Disposable cache failures never damage durable attention state. Limits and deletion semantics are in [configuration](CONFIGURATION.md#optional-recent-message-cache).


### PR #23 cache provenance and revoked-read recovery

Recent disk-window freshness is independent of older-page loading. A successful older page retains the original fetched time and cached provenance, plus a separate recent-refresh failure until a new recent request starts. Older loads do not feed unrefreshed cached timestamps into local activity/read observation. Only a successful recent refresh or an explicit replacement window can clear cached provenance.

An explicit conversation access denial cancels and rotates that conversation's read context/generation, cancels its active profile/follow lookup, releases invalidated metadata/startup busy state, and purges visible/disk content. Late metadata/history/reply/profile results are rejected. Fresh retries use a new read context; other conversations, durable attention, drafts and delivery acknowledgements retain their independent lifecycles. Purged timelines retain the access error for actionable recovery rather than an indefinite loading state.


## Workspace sessions and participation (0.7)

The CLI authenticates OS-keyring credentials and passes services plus verified identities to `ui.Accounts`. The registry contains display identity and a legacy-owner retirement marker only; an environment override runs one account without registering its secret. Every session owns its full view, cache, attention/source state, drafts and deliveries. Preferences now use `store.AccountKey` (workspace/user); existing account-hashed stores keep their names. Legacy preferences are claimed once, not copied to every user of a workspace.

Only the active model receives input and refresh ticks. On switching, the coordinator cancels its read context, invalidates its activation epoch and discovery/profile/follow generations, and clears abandoned busy guards. All command results carry their originating session and epoch, including private Bubbles clipboard/cursor results. Only explicitly marked terminal commands and quit messages bypass that routing. The selector consumes widget completions while open; obsolete widget epochs cannot alter another account or appear after switching back. Focused input timers restart after selector dismissal or account activation. Obsolete results cannot publish or advance checkpoints, even after switching back. Queued canceled read commands return before invoking the service. Accepted partial activity and completed checkpoints remain intact. Activation creates new read contexts and promptly checks enabled sources, retries unfinished metadata/directory restoration and refreshes the current live view if it is at newest. Scrolled views retain their anchor; their live history resumes at newest or explicit refresh. The existing scroll state owns selection behavior: at newest both viewport and selection follow incoming pages, while explicit browsing retains message identity. Account coordination does not override that distinction. One retained client per account preserves method pacing and server backoff across switches. Inactive counts are omitted.

Sends capture the original service, application context and immutable target/body. Send, reaction and explicit open-in-Slack completions route to their owning session even while inactive; no switch triggers a write or retry. Reaction toggles read current own-user state then make at most one add/remove, treating a concurrent already-present/already-absent response as the intended state. Mutations are single-flight per account and never dismiss attention. Permalinks use `chat.getPermalink` for the selected timestamp, then an argv-only platform opener restricted to Slack HTTPS domains. Demo reactions remain memory-only; demo browser opening is unavailable. Global exit protection includes every retained draft and pending/failed send.


## Dependable daily use (0.8)

Reading anchors are captured on the event loop before page merges, width/height changes and profile decoration changes. Numeric scrolling preserves the top visible message identity plus its wrapped-row offset; selection-following remains derived from the selected message and newest-following remains scroll zero. Selection is restored by timestamp, falling forward on deletion and clamping to retained context on eviction. Scroll keys keep the action target within the visible window. Available height, changed wrapping within an edited message and bounded-cache eviction limit exact row preservation. Rendering still performs no mutation or I/O.

Timelines retain recent-refresh and page errors independently, plus the last successful recent-check time. Older-page success cannot clear a failed recent refresh or make a cached window fresh. The `v` recovery modal derives bounded, scrollable details from all retained timeline/source state; transient status actions cannot erase it. Input/paste is consumed by the modal while typed service results continue to apply.

Partial thread views advance only on explicit page requests, not background ticks. The timeline owns `ReplyThrough`, advanced only by successful fetched reply pages and reset on an anchored replacement or access purge. Display merges and send acknowledgements never advance it. Commands capture that fetched boundary and permit one extra paced read after `invalid_cursor`, using that timestamp as an exclusive lower bound. Empty/repeating cursors fall back to timestamp continuation; a page making no timestamp progress remains visibly incomplete. Useful messages are deduplicated into a maximum 300-message window; an available thread root is retained within that bound. Follow-source discovery remains separately bounded and unchanged.

`ui.Account.Reload` is a CLI-owned callback returning a validated service/identity, never a token. Navigation Ctrl+R schedules one check per account. Explicit `--login --account` validates identity and writes only the registered keyring slot, so it can coexist with the running UI as the sole preference writer. The callback reads that slot and authenticates an immutable replacement client. CLI and coordinator both refuse identity changes. Environment sessions revalidate their inherited value without persisting it; changing the shell environment cannot replace a running process’s value.

Successful reload invalidates old read epochs, adopts the service and resumes active-only bounded work without replacing the model/drafts/outbox. Completion while inactive adopts the service without starting reads. Old writes retain their original client/token and completion ownership. Their credential generation prevents a late old-token authentication failure from stopping the replacement session. Slack clients share a lock, method deadlines and bounded name caches across replacements; even a late Retry-After from an original write remains authoritative. No mutation is automatically retried.

Freshness status uses an event-loop-owned clock updated by the existing three-second tick and accepted history results. Views read that clock without consulting wall time. Initial loading, cached provenance, partial coverage and errors stay visible; routine polling/completion is silent, with a stale indicator only beyond 30 seconds since the selected timeline’s last successful recent fetch. Older-page loads and unrelated timelines cannot renew that timestamp.

Persistent credential/delivery recovery is derived from account and outbox state after transient action feedback clears. Uppercase names remain searches; ambiguous IDs have an explicit id: form, and matching names take precedence over shorthand ID detection. Unresolved live directory pages preserve known names/handles for the same DM participant while an independent pending-name set allows paced enrichment to continue. Kept removal does not require cached access revalidation.

Saved DM metadata uses cached participant names or the user ID immediately, matching directory pages. Active DM participant names and message authors/mentions resolve through the bounded, cancelable foreground profile stream; successful lookups enrich labels without delaying history or changing account, message selection or drafts.

History wrapping reserves one right padding column and a shared blank-plus-rail gutter. Selected messages render the rail independently in the accent color beside the existing arrow/header style and all body rows; unselected messages reserve matching blank cells. Internal blank lines retain the rail, while inter-message separators do not. The context row and continuation header share the history right-padding policy; reading anchors and fill calculations use the same wrapped rows. Formatting decorates display rows only and does not alter stored/copied message content.

Message cursor navigation computes the existing visible row window before changing the action target. Fully visible targets retain that window; crossing the upper/lower boundary reveals the target, and oversized messages start at their header. A named pinned-newest scroll state freezes the latest viewport while pausing automatic following, independently of which visible message is selected. It participates in reading-anchor and visible-selection preservation; explicit G resumes newest following. Selection rails use a shared gutter, so changing selection does not alter wrapping or row counts.

Thread arrow/Enter shortcuts are routed after modal, picker and composer handling. In channel-message navigation, a readonly selected-message check allows Right Arrow or Enter to open an existing thread only when the reply count is positive. Enter otherwise retains composition, i composes directly and t retains explicit thread opening on any message. Left Arrow reuses the existing Esc thread-exit path. Navigation repeat events cannot chain thread transitions; text input keeps its normal repeats and cursor handling.

Pinned viewports retain both their first source row and leading blank display rows. Reading anchors carry that padding through resize, profile enrichment and delayed history results, so sparse browsing never silently becomes bottom-aligned following. Rendering, selected-target visibility and navigation share the same viewport bounds. Page movement derives its starting offset from the current pinned source row. Continuation ownership is computed after start-row adjustment and excludes inter-message separators. Direct cached-DM verification merges unresolved participant-name fallbacks with the existing same-participant hint before persisting it; a failed optional profile lookup does not discard the known name/handle.

Account-wide resize first applies local-only layout/anchor updates to every initialized session. The coordinator then returns only the active session’s eligible history-fill command, wrapped with that account’s epoch. Inactive sessions resize without marking reads busy or consuming fill budgets. Standalone models use the same local resize helper before scheduling their own fill.
